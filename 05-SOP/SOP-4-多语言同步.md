# SOP-4 · 多语言同步

**核心原则**：一个 `article_id` = 一篇文章 = 七个语言版本。
**内链关系设计一次，七个语言版本继承；只有锚文本需要翻译。**

支持语言：`zh-Hant` `zh-Hans` `en` `ja` `ko` `vi` `th`

---

## 一、关键词在多语言下怎么算冲突

**唯一性按 `(lang, primary_keyword)` 判定。**

- 繁中「OpenX 註冊」与日文「OpenX 登録」→ **不冲突**，它们是同一篇文章的两个语言版本。
- 繁中「OpenX 註冊」与简中「OpenX 注册」→ **不冲突**（不同 lang），但如果它们属于**不同的 article_id**，那是导入配对出了问题，按 SOP-3 Step 2 重新配对。
- 同一语言内两个 article_id 抢同一个词 → 冲突，走 SOP-1。

繁简之间要特别小心：繁简转换后的词高度相似，容易被误判成同一篇。**判定依据是 `article_id`，不是字面相似度。**

## 二、翻译前的准备

1. 源语言版本必须已经 `ready`（走完闸 1 + 闸 2，内链已插入）。
2. 确认每个内链目标文章的**目标语言版本是否存在**：

```bash
python3 "工具/openx_audit.py" langcheck --article OX-0002 --lang ja
```

3. 把源文的 `outbound_links` 拆成两类：
   - **可继承** —— 目标文章的目标语言版本已存在 → 保留链接，翻译锚文本。
   - **待补** —— 目标语言版本不存在 → **删除该链接**（保留句子，去掉链接标记），并写进 `内链矩阵` 待补队列。

**绝不允许**：链到不存在的页面、跨语言链（日文页链到繁中页）、链到自动机翻的占位页。

## 三、锚文本翻译

不是把源语言锚文本直译，而是**取目标文章该语言版本的 `anchor_offers`**。

查 `01-索引/术语与锚文本表.md` → 找到目标 `article_id` 的锚文本池 → 取目标语言那一栏 → 选一条与上下文最顺的。

若该语言的锚文本池为空，先补池子再翻译，不要临时直译。

## 四、与既有翻译 skill 的分工

翻译本身**不由本系统做**，交给：

| 语言 | skill |
|---|---|
| zh-Hant → zh-Hans / en / ja / ko / vi / th 批量 | `1000x-article-translator` |
| 中 → 英 | `web3-zh-en-translation` |
| 中 → 日 | `web3-zh-ja-translation` |
| 中 → 韩 | `web3-zh-ko-translation` |
| 中 → 越 | `web3-zh-vi-translation` |
| 中 → 泰 | `web3-zh-th-translation` |
| 多语言成品审查 | `web3-multilang-audit` |

**本系统在翻译前后各做一件事**：

- 翻译前：给出「可继承 / 待补」的内链清单 + 目标语言锚文本，作为翻译输入。
- 翻译后：登记语言版本状态、回填 `url`、更新语言版本矩阵、清待补队列。

术语库以翻译 skill 的为准；只有 OpenX 站点专有词写进 `01-索引/术语与锚文本表.md`。

## 五、翻译后回写

1. `文章总表` → 语言版本矩阵对应格子改为 `translated` 或 `published`。
2. `文章总表` → 已发布 URL 登记加一行（该 lang 的 slug + url）。
3. 该语言版本文件的 frontmatter：`lang`、`source_lang`、`url`、`publish_date`、以及**实际保留下来的** `outbound_links`（可能比源语言少）。
4. 被删掉的链接 → 待补队列，标注 `原因：目标语言版本未上线`。

## 六、语言版本不同步的处理

各语言版本上线节奏不同是常态。约束只有两条：

- 目标语言版本不存在 → 不链，不占位。
- 新语言版本上线 → **必须**回头扫一遍待补队列，把当初删掉的链接补回去。

```bash
python3 "工具/openx_audit.py" scan --lang ja
```
